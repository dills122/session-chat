# Spec: inviter join transaction v1

Status: implementation contract; restartable pre-membership authorization
states specified under ADR 0023; durable invitation opening context and
authorization-shadow transitions,
fault-injectable membership model, SQLCipher durable Welcome owner, and real
capability-admission/MLS composition implemented

## Objective

Define the single inviter-local commit required by ADR 0008 and ADR 0012. One
successful commit makes the following facts visible together:

- the exact invitation generation is consumed;
- the exact join request is retained as replay state;
- the approval result is retained;
- the inviter's advanced MLS group snapshot is retained; and
- the encrypted Welcome and its deposit-only destination are pending in an
  outbox under one idempotency key.

Network delivery is never part of this transaction. A delivery or
acknowledgement failure cannot release the invitation, erase replay state, or
roll back the MLS epoch.

The first implementation is a deterministic, bounded, fault-injectable memory
model. The `storage-sqlcipher` laboratory passes the durable Welcome-owner
subset across close/reopen and schema migration. A retained real
capability-admission/MLS integration holds a one-shot durability-pending result
until recovery resolves the SQL outcome. These adapters do not establish
rollback resistance, production readiness, or durable-client integration.

## Restartable pre-membership authorization

ADR 0023 extends the transaction boundary backward without serializing live
membership authority. One inviter-local durable owner now has two related but
distinct records:

1. an active invitation generation with its exact canonical signed invitation
   and exact invitation-scoped HPKE private key; and
2. a non-authorizing authorization shadow created after automated verification
   and exact invitation reservation.

The opening context commits before the invitation descriptor is shared. It is
bounded to at most 512 canonical invitation bytes plus one exact 32-byte HPKE
private key. Load must re-run canonical/signature validation and prove the key
matches the invitation's exact HPKE public key. Expired, consumed, unsupported,
missing, malformed, or mismatched opening state is never returned as
`Available` and cannot be regenerated under the old generation.

The authorization shadow owns this closed record:

| Value | Bound or invariant |
| --- | --- |
| Authorization-attempt ID | exactly 16 nonzero provider-generated bytes |
| Invitation ID | exactly 16 nonzero bytes |
| Invitation generation | exact 64-byte signed-record signature |
| Join request ID | exactly 16 nonzero bytes |
| Request nonce | exactly 32 nonzero bytes |
| Intended verifier | exact 32-byte invitation-scoped Ed25519 key for capability v1 |
| KeyPackage binding | exact reference, MLS version/ciphersuite, credential identity/type, and leaf signature key from ADR 0009 |
| Request fingerprint | exact SHA-256 digest over the canonical protected request |
| Expirations | exact request and invitation expirations; request does not outlive invitation |
| State | one closed state below, plus an exact nonzero transaction ID only where required |

The Phase 1 owner policy is stored with the database and permits only 1 through
8 live invitation generations and 1 through 8 retained unexpired authorization
attempts. Reopen with different limits fails closed. Capacity exhaustion rejects
new work without eviction or partial mutation.

The shadow explicitly excludes canonical KeyPackage bytes, parsed provider
objects, HPKE-open plaintext, provider proof, bearer capability, invitation
private key, pending MLS state, and group secrets. Its fields detect replay and
conflict but cannot authorize membership.

```text
PendingApproval
  | explicit approve
  v
ApprovedPendingMembership
  | persist exact transaction ID before membership storage may begin
  v
MembershipOutcomeUnknown
  | authorized membership write commits atomically
  +--> Committed
  `--> exact recovery proves no commit --> Abandoned

PendingApproval ----------> Rejected | Abandoned
ApprovedPendingMembership -> Abandoned
```

An explicit rejection and a process restart in either pre-membership live state
terminalize that authorization attempt, retain its request ID, nonce, and
fingerprint through the invitation-generation expiry, and release only the
matching invitation reservation. The generation returns to `Available` only
when its exact opening context reloads and remains valid; otherwise it becomes
terminally `Unusable`.

Once membership storage may have begun, the provider-applied Add owns a
non-forgeable one-shot binding to that exact in-memory group instance and state
revision. It exposes the storage-only binding solely while staging and then
immediately invokes the provider write; any intervening operation that could
change the serialized MLS snapshot invalidates the authority before staging.
The binding also carries a one-shot provider-write authority activated only on
the originating thread around that immediate callback. The MLS adapter's
provider-facing storage wrapper records a domain-separated SHA-256 digest of
the exact serialized group state and ordered epoch insert/update records before
delegating to caller-supplied storage. The durable owner accepts only the same
bytes under that active authority, so another same-group callback or a
delegating wrapper that substitutes state fails closed.
The write transaction revalidates its exact KeyPackage reference, credential
identity, leaf key, group, epoch transition, Welcome, and one-shot authorization
under the same database lock used for MLS, outbox, authorization, and invitation
updates. Expiry is evaluated there using staging time advanced by monotonic
elapsed time, so lock wait, suspension, or application delay cannot preserve a
stale authorization. A recovery that first proves the exact
transaction absent records `Abandoned` and fences any staged writer. An
ambiguous, unavailable, malformed, or conflicting recovery result remains
`MembershipOutcomeUnknown`. Only the atomic authorized commit consumes the
invitation, and only a proven absent or uncommitted result may abandon the
attempt and release it. Recovery never repeats MLS Add.

Known cancellation before approval uses the exact live
`PendingApproval -> Abandoned` transition. Legacy reservation and inviter paths
reject generations present in the opening-context ledger. Store-open validation
rejects contradictory terminal authorization, opening, inviter-result, and
compatibility-reservation rows.

## Assumptions

1. Capability verification, exact KeyPackage ownership, automated policy, and
   explicit simulated approval complete before the membership transaction
   begins. The durable authorization shadow is already bound to that live
   attempt, but does not replace its provider-owned value.
2. The MLS provider has prepared and applied exactly one Add, and supplies the
   complete post-Add snapshot required to reload that group without repeating
   the Add.
3. The Welcome is already MLS-encrypted. Its bytes and deposit-only endpoint
   are nevertheless sensitive metadata and must not enter logs.
4. Invitation identifiers and request identifiers are not sufficient to name a
   reservation. The exact invitation record signature is the generation token
   that prevents stale-reservation ABA after expiry and reissue.
5. ADR 0017 selects SQLCipher for the bounded durable laboratory. Product
   storage, platform key custody, rollback resistance, and secure deletion
   remain separate decisions and evidence gates.

## Owned record

Each commit is selected by a provider-generated, nonzero 16-byte transaction
identifier. The committed record owns these bounded values:

| Value | Bound or invariant |
| --- | --- |
| Transaction ID | exactly 16 nonzero bytes |
| Invitation ID | exactly 16 nonzero bytes |
| Invitation generation | exact 64-byte signed-record signature |
| Join request ID | exactly 16 nonzero bytes |
| Request fingerprint | exact 32-byte digest over the canonical protected request |
| Group ID | non-empty, at most 255 bytes |
| Epochs | `epoch_after == epoch_before + 1` |
| Approval record | non-empty, at most 4 KiB |
| MLS group snapshot | non-empty, at most 2 MiB |
| Welcome envelope | non-empty, at most 64 KiB |
| Deposit endpoint | non-empty, at most 4 KiB |
| Outbox expiry | later than commit time |

The model and future adapters use exact byte equality for idempotent recovery.
Reusing a transaction ID with any different field is rejected. Reusing an
invitation generation or join request under a different transaction is also
rejected.

## State transitions

Before commit, the exact invitation generation is `Reserved` by the exact join
request. Commit has only two externally recoverable outcomes:

```text
Reserved
  | atomic commit
  v
Consumed + ReplayRetained + Approved + MlsAdvanced + OutboxPending
```

- A known failure before commit creates no committed MLS or outbox record. The
  durable authorization shadow and replay record remain until the owner proves
  the transaction uncommitted, records `Abandoned`, and releases only the exact
  invitation reservation.
- A success returns `Committed`.
- An identical retry returns `AlreadyCommitted` without applying MLS again.
- A crash or lost response after commit is recovered by transaction ID and
  returns the already-committed record.
- A conflicting retry fails closed.

The in-memory conformance model injects failures at every staging boundary and
immediately after the atomic state swap. A durable adapter must additionally
run process-crash and storage-fault tests against the real engine.

## Outbox transitions

The committed Welcome starts `Pending`. A worker may lease it for one bounded
delivery attempt and then report either outcome:

- failure or an expired lease returns the same item to `Pending`;
- success marks it `Delivered`; and
- duplicate success for the same transaction is idempotent.

The durable SQLCipher adapter additionally retains `AttemptsExhausted` and
`Expired` terminal states so restart enumeration cannot resurrect work after
its configured attempt or lifetime bound. Its version-2 row persists the
attempt count, monotonically renewed lease generation, opaque lease identity,
and lease expiry. A result must match the exact persistent store identity plus
transaction/generation/lease tuple.

Leasing, retrying, expiring, or completing delivery never mutates invitation,
replay, approval, or MLS state. Delivery uses the transaction ID as the stable
local idempotency key. The remote transport still enforces its own exact
envelope idempotency contract.

## Recovery API

Recovery accepts only the exact transaction ID and returns a secret-free view:

- whether the atomic commit exists;
- the committed epoch;
- whether the outbox is pending, leased, delivered, exhausted, or expired; and
- the current delivery-attempt count.

The full stored record is borrowed only by the delivery integration. It does
not implement `Debug`, `Display`, or serialization through a generic object
graph.

## Security and resource rules

- Validate all lengths, nonzero identifiers, epoch arithmetic, and expiry
  before allocating or changing state.
- Bound committed records, outstanding transactions, delivery attempts, and
  lease duration.
- Never evict a committed membership or pending outbox item to make room.
- Never log or include the MLS snapshot, Welcome, destination capability,
  invitation generation, approval evidence, or request fingerprint in errors.
- Do not accept generic maps, extensions, accessors, symbols, or recursively
  cloned values at this boundary. Inputs are concrete byte strings and scalar
  fields only.
- A copied durable store must not reveal secrets without an unsealed
  client-vault key. Database encryption alone does not provide rollback
  resistance; that remains a separate platform/storage requirement.

## Required evidence

The conformance suite must prove:

1. every injected pre-commit failure leaves only the original reservation;
2. an injected post-commit lost response recovers one complete commit;
3. identical retry is idempotent and conflicting retry is rejected;
4. stale invitation generations and duplicate request IDs cannot commit;
5. delivery failure and lease expiry preserve the committed membership and
   pending Welcome;
6. delivery success changes only outbox state;
7. all byte, capacity, attempt, time, and arithmetic bounds fail closed; and
8. secret-bearing records have no accidental `Debug` or generic serialization
   surface;
9. the SQLCipher durable-owner issuance API does not return its publishable
   invitation before the exact opening context commits, and reload rejects a
   missing, mismatched, malformed, or expired context; lower-level provider
   generation remains non-durable and the P1-3 composition must use the owner
   API before publication;
10. restart from `PendingApproval` or `ApprovedPendingMembership` records one
    terminal abandonment, retains replay state, and conditionally returns only
    the exact usable generation to `Available`; and
11. `MembershipOutcomeUnknown` neither repeats MLS Add nor releases the
    invitation until exact transaction-ID recovery proves an allowed outcome;
    and
12. a concurrent proven-noncommit recovery fences a staged authorized writer,
    while known failure and ambiguous post-commit results finalize in the same
    open scope.

## Deferred durable adapter gate

Before claiming durability, select and record the storage engine, transaction
mode, vault-key lifecycle, file permissions, secure-delete limitations, backup
behavior, corruption handling, rollback detection, migration policy, and MLS
provider storage integration. The adapter must prove that the MLS snapshot and
all Session Chat rows share one real atomic commit. If the selected MLS storage
hook cannot participate in that commit, it is unsuitable for this boundary.
