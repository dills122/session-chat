# Local transport capability-boundary evidence

Status: implemented local evidence beside the narrow provider-neutral trait;
generalized request/receipt capability representation and network-provider
issuance remain unimplemented

Date: 2026-08-20

## Scope

This record maps ADR 0010's right separation to the implemented one-Welcome
memory adapter. It hardens the local compatibility boundary beside the narrow
provider-neutral `EnvelopeTransport` trait and separate deterministic memory
adapter already retained on `master`. It does not define provider-neutral
capability bytes, create rotation authority for the local profile, or claim that
a real mailbox protocol has passed these checks.

## Ownership and exposure matrix

| Value | Owner and permitted movement | Clone/debug/display | Serialization | Destruction and retained form |
| --- | --- | --- | --- | --- |
| `LocalWelcomeDepositEndpoint` | Generated by the local adapter and deliberately transferred to the approved sender | Non-`Clone`, non-`Debug`, non-`Display` through its secret-bearing protocol fields | One reviewed canonical encoding for the protected join response | Embedded `DepositCapability` zeroizes on drop; the adapter retains only a domain-separated digest |
| `LocalWelcomeReceiveCapability` | Retained by the joiner and borrowed only by `receive` | Compile-fail evidence rejects `Clone`, `Debug`, and `Display` | No serialization API | Secret bytes zeroize on drop; the adapter retains only a domain-separated digest |
| `LocalWelcomeAcknowledgementCapability` | Retained by the joiner and borrowed only by `acknowledge` | Compile-fail evidence rejects `Clone`, `Debug`, and `Display` | No serialization API | Secret bytes zeroize on drop; the adapter retains only a domain-separated digest |
| `DeliveryId` | Returned with a received envelope and used only to select an item | Copyable and diagnostic because it is explicitly non-authority | No generalized wire contract exists | Cannot satisfy an acknowledgement-authority type position |
| Rotation authority | Not issued by the local one-use profile | Not applicable | Not applicable | A reusable provider must define issuance, scope, revocation, replacement, and destruction before adding this right |

Crate-only capability constructors and raw-secret accessors keep issuance and
verification inside `session-transport`. Public callers can receive and consume
the right-specific values but cannot assemble local receive or acknowledgement
authority from raw bytes.

## Retained tests

`crates/session-transport/src/capability.rs` retains compile-fail examples that
prove:

- deposit, receive, and acknowledgement authority are not `Debug`, `Display`,
  or `Clone`;
- deposit, receive, and acknowledgement rights cannot occupy one another's
  typed positions; and
- a `DeliveryId` cannot occupy an acknowledgement-authority position.

`crates/session-transport/tests/redaction.rs` injects known ASCII authority and
ciphertext bytes through a structurally valid but foreign deposit. Both
`Display` and `Debug` remain the exact coarse rejection and contain neither
seeded byte sequence.

The unchanged `local_welcome_mailbox.rs` suite continues to prove generated
right separation, foreign/expired rejection, exact retry, conflicting deposit,
expiry, deletion, and capacity behavior after the capability-module extraction.

## Explicit gaps

- No provider-neutral capability representation or erasure boundary exists.
- The narrow synchronous `EnvelopeTransport` trait exists, but no complete
  budget-aware request/receipt, polling, cursor, or mailbox-lifecycle boundary
  exists.
- The local profile issues no rotation capability.
- No cursor, receipt, batch, profile binder, coordinator, durable adapter, or
  network adapter is exercised.
- Rust type and diagnostic evidence does not prove process isolation, packet
  privacy, revocation, crash recovery, or production secret erasure.
