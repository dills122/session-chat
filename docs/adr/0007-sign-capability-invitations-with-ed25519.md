# ADR 0007: Sign capability invitations with Ed25519

Status: accepted for the Phase 1 invitation contract

Date: 2026-08-16

## Context

ADR 0005 selected deterministic CBOR but deliberately left the invitation
signature suite and domain separation open. The next Phase 1 increment needs a
small reviewed signature implementation for invitation integrity, exact wire
fixtures, and replay-safe state tests. It does not need a global identity key,
credential format, HPKE suite, or MLS ciphersuite.

An invitation carries its own verifying key. That makes the descriptor
self-authenticating against mutation, but it does not establish who controls
the key. The invitation-sharing channel, an out-of-band fingerprint, or future
admission evidence must provide that higher-level binding.

## Decision

Use RFC 8032 Ed25519 through exactly `ed25519-dalek` 3.0.0 for version 1 signed
capability invitations. Enable only its `fast` and `zeroize` features; do not
enable key generation, batch verification, PKCS#8, PEM, digest, legacy
compatibility, or hazardous low-level APIs in `session-protocol`.

Use plain Ed25519 over this application-defined message:

```text
"session-chat/signed-invitation/v1" || 0x00 || canonical_unsigned_invitation
```

The zero-terminated constant is an unambiguous application-domain prefix. The
unsigned invitation is the deterministic 11-field CBOR array specified in
`docs/specs/SIGNED_INVITATION_V1.md`. It includes the protocol version, object
type, signature suite, admission mode, use policy, time interval, invitation
ID, join challenge, bearer capability, and verifying key. A signature cannot
therefore be moved to another Session Chat purpose or have any of those fields
changed.

Verification uses `VerifyingKey::verify_strict` so weak public keys and both
documented Ed25519 signature-malleability classes are rejected. Accepted wire
bytes must also pass ADR 0005's decode/re-encode equality check.

Invitation signing keys are invitation-scoped and generated by a higher layer
using an operating-system CSPRNG. `session-protocol` accepts a caller-provided
signing key and does not own generation or persistence.

## Alternatives considered

### Ed25519ph with the RFC 8032 context mechanism

Rejected for this small fixed-size object. In `ed25519-dalek` 3.0.0, contexts
are exposed for Ed25519ph behind the `digest` feature. Prehashing adds another
mode and dependency surface without a large-message or streaming requirement.
The fixed application prefix gives this protocol an explicit, testable domain
boundary while retaining plain Ed25519 interoperability.

### A signature over the CBOR bytes without a domain label

Rejected. A key accidentally reused for another object type could validate the
same bytes in another protocol context. The explicit label makes the intended
use part of every signing and verification operation.

### A long-lived device or external-identity key

Rejected. It would increase cross-session linkability and conflict with ADR
0002. External identity remains optional admission evidence bound to fresh
session material.

### HMAC with the bearer capability

Rejected. Anyone who can open the invitation knows the capability and could
rewrite the descriptor. It would also conflate bearer admission authority with
inviter authentication.

## Consequences

- The first invitation object has one explicit, allowlisted signature suite and
  stable cross-implementation bytes.
- Capability invitations remain secret bearer objects and are not safe for
  public posting.
- Self-contained signature verification proves integrity and key possession,
  not GitHub identity, personhood, trust, or channel authenticity.
- New signed object purposes require a different domain label and fixtures.
- Algorithm agility is deliberately rejection-based in version 1; adding a
  suite requires a new reviewed contract rather than a silent fallback.
- HPKE, admission-proof binding, MLS, durable replay state, and key storage
  remain separate decisions.
